# Software Requirements Specification (SRS)

## PhD Scholar Management & Academic Tracking System

**Version:** 1.0
**Date:** September 2026
**Project Type:** Web-Based Academic Management System
**Primary Users:** PhD Students, Supervisors/Faculty, Administrators

---

# 1. Introduction

## 1.1 Purpose

The purpose of this system is to provide a centralized web-based platform for managing and tracking the academic journey of PhD scholars.

The system will allow PhD students to:

* Maintain their academic profile.
* Track semester-wise academic work.
* Manage courses and credits.
* Upload and manage academic documents.
* Access and submit required forms.
* Track deadlines and upcoming events.
* Maintain their degree timeline.
* Manage thesis-related information.
* View their Supervisor and SRC Committee.
* Receive notifications regarding deadlines, approvals, and events.

Supervisors/Faculty will be able to:

* View their assigned students.
* Monitor students' academic progress.
* View student records semester-wise.
* Schedule events for one or multiple students.
* Approve/reject thesis submissions and other student requests.
* Approve requests to become a Supervisor or SRC Committee member.

Administrators will have complete control over the system, including student/faculty management, supervisor assignment, SRC committee management, event management, and profile modification.

# 3. Functional Requirements

# 4. Authentication & Registration

## FR-01 Student Registration

The system shall allow a student to register using their official college email/College ID.

### Registration Flow

1. Student opens the website.
2. Student selects **Register**.
3. Student enters their College ID / official college email.
4. System validates the College ID/email.
5. System sends an OTP.
6. Student enters the OTP.
7. System verifies the OTP.
8. Account is created.
9. Student is redirected to the Login page.
10. Student logs in.
11. If this is the student's first login, the system redirects them to **Complete Profile**.

---

## FR-02 Student Login

The system shall allow registered students to log in.

The system shall authenticate the user and determine their role.

The system shall redirect the user to the appropriate dashboard:

* Student → Student Dashboard
* Supervisor → Supervisor Dashboard
* Admin → Admin Dashboard

---

## FR-03 Faculty Login

Faculty/Supervisors shall use credentials created by the Administrator.

Faculty shall not have public registration.

---

## FR-04 Admin Login

The Admin account shall be controlled by the system and shall not be available through public registration.

---

## FR-25 Thesis Approval

When a student submits a thesis/document requiring Supervisor approval:

1. Supervisor receives a notification.
2. Supervisor opens the request.
3. Supervisor reviews the document.
4. Supervisor approves or rejects it.
5. System records the decision.
6. Student receives a notification.

Possible statuses:

* Draft
* Submitted
* Under Review
* Approved
* Rejected
* Resubmission Required

# 29. Important Business Rules

### BR-01

A Student must belong to exactly one student category:

* Regular
* Part-Time

### BR-02

A student can have one primary Supervisor.

### BR-03

A Co-Supervisor, if supported, is optional.

### BR-04

A student may have an SRC Committee according to departmental rules.

### BR-05

Students can only view their own academic records.

### BR-06

Supervisors can view records of students assigned to them.

### BR-07

Admins can view and manage all records.

### BR-08

A course submitted by a student shall remain pending until approved by the appropriate Supervisor.

### BR-09

A thesis requiring approval shall remain pending until reviewed by the appropriate Supervisor.

### BR-10

Only eligible students shall be selectable for an event requiring eligibility rules.

### BR-11

Important actions shall generate notifications where applicable.

### BR-12

Deleted academic records should preferably be soft-deleted rather than permanently removed, especially when auditability is required.

# 30. Open Decisions / Requirements Requiring Confirmation

The following points need to be finalized before implementation.

## OD-01 College ID vs College Email

The registration requirement mentions both:

* College ID
* College email

**Recommended approach:** Use the official college email for OTP verification and College ID as the unique student identifier.

---

## OD-02 Student Registration Approval

Currently registration appears to happen automatically after OTP verification.

Need to decide whether:

**Option A:**
OTP verification → account immediately created.

**Option B:**
OTP verification → Admin approval → account activated.

---

## OD-03 Supervisor Assignment

Need to decide whether students can request/select their Supervisor themselves.

Recommended workflow:

```text
Student selects Faculty
       ↓
Faculty receives request
       ↓
Faculty approves
       ↓
Admin confirms/assigns
       ↓
Supervisor becomes active
```

Admin should always retain the ability to override/change the assignment.

---

## OD-04 SRC Committee

Need to finalize whether:

* Only Admin can create the SRC Committee, or
* Student can propose members and faculty must approve.

Recommended:

```text
Student/Admin proposes faculty
          ↓
Faculty Approval
          ↓
Admin Final Confirmation
          ↓
SRC Committee Created
```

---

## OD-05 Semester Structure

The number and naming of semesters should be configurable.

The system should **not** hardcode only a fixed number of semesters.

---

## OD-06 Deadline Rules

Need to define which deadlines are:

* Automatically generated.
* Created by Admin.
* Created by Supervisor.
* Student-specific.
* Semester-specific.

---

## OD-07 Eligibility Rules

The department should provide rules for determining whether a student is eligible for each event.

Example:

```text
Event: Comprehensive Examination

Eligible if:
Semester >= X
AND required courses completed
AND required credits >= Y
```

These rules should preferably be configurable.
