# Performance / Latency Review — CSE_portal

Reviewer: Performance Reviewer (read-only). Stack: Express 4 + Mongoose 8 + Mongo (backend), React 19 + Vite 6 (frontend).
Baseline (controller-verified): all gates pass on `b6924f0`. 4 read-only reviews run in parallel.

## Summary

The system is **fundamentally healthy**. Ideal architecture already in place: React.lazy code-splitting (main chunk **80.39 kB gzip**, every page its own 1–10 kB chunk), near-zero third-party runtime deps, eager auth pages kept small, graceful-passive rate limit (`100 req/15min` applied to **all** `/api` routes including auth), and **no unbounded query params** — every `limit` clamp is `min(100, ...)`, every `page` is `max(1, ...)`. Index coverage is good for the app's primary access patterns (`Milestone {student,key}`, `Credits {student,semester}`, `Notification {user,createdAt}`, `Semester {student,semesterNumber}`, `RefreshToken {user,expiresAt}`), and Mongoose populates are used instead of hand-rolled joins.

The main risks are all **scale-triggered loops that turn O(n) work into O(n) sequential network round-trips** in a few hot paths (deadline scheduler, event creation, participant resolution) plus a handful of missing collection-wide indexes that are only noticeable once a collection grows. Nothing is Critical at today's scale (~6–200 students), but several Important items will bite as cohort size grows and are cheap to fix now.

No re-render fire, no bundle waste, no heavy eager imports, no static assets at all (frontend has zero files under `public/` and `assets/`).

## Estimated benefits for the Important items (quantified)

- **#1 + #11 (scheduler):** 100-student global deadline today = ~300 serialized DB/SMTP ops (~30–120 s, possibly overlapping the 6h interval). With index (#7) + `$in`/bulk + parallel emails → ~6 DB ops + 100 concurrent SMTP sends (seconds, non-blocking). Also permanently fixes semester-deadline silent no-op.
- **#2 + #3 (event create):** P=50 → serial 100+ round-trips + 50 emails in request path (~30 s). After fix → ~4 round-trips, response under ~100 ms, emails in background.
- **#4 (student dashboard):** ~10 sequential queries (~sum of 6-7ms Mongo + 2 aggregates ~10-20ms) → `Promise.all` to ~40-60ms total on the student's most-visited page. Roughly 2-4x faster dashboard TTFB.
- **#6 (StudentCourse index):** turns a collection scan (current) into an index seek on every credits computation; at 1-5k docs this is the difference between ~40-150 ms and ~2-5 ms per dashboard/detail/timeline.
- **#8 (admin pickers):** 200 full-doc payloads (~150-250 KB) → lean select (~20-40 KB) per page; also fixes >100-student picker blindness.
- **#9 (register):** removes blocking SMTP from request path → signup latency no longer depends on mail server.
- **#10 (/auth/me):** -1 student-profile query and ~10-20 KB unused payload on every app boot.

## MUST-fix before merge

1. **deadlineService semester-scope bug + serialization (#1/#11)** — silent functional bug (semester deadlines never notify anyone) + 30-120 s event-loop-blocking chain at cohort scale. Fix with bulk notifications, `$in` user/email resolution, parallel emails; add `{notificationSent, dueDate}` index (#7).
2. **Event-creation blocking email fan-out (#2) + participant N+1 (#3)** — request latency tied to SMTP for every participant; cheap O(1)-round-trip fix with existing `createBulkNotifications`.
3. **StudentCourse index (#6)** — hottest unindexed collection; one-line fix, immediate benefit to dashboard/credits/timeline aggregates.
4. **getAssignedStudents name filter (#5)** — wrong results/pagination, minimal fix.
5. **Admin picker payloads (#8)** — 150-250 KB per page + hides students beyond 100.

All remaining (Important-only) items are low-risk, high-value and recommended in the same pass (#4 Promise.all dashboard, #9 OTP email async, #10 slim `/auth/me`, #12 notifications pagination). Minors (#13-20) are backlog-worthy; #21/#22 document that bundle/render/asset hygiene is already excellent.

## Questions / concerns

- **MongoDB not installed locally** — no index-level `explain()` was possible; index-impact estimates are model-based, not measured on a live dataset. Worth an `explain("executionStats")` pass against the Atlas DB for `StudentCourse`/`Deadline` after seeding a few thousand rows.
- **Semester-scoped deadlines appear entirely untested** (scheduler fires immediately only at server start; no unit test covers `checkDeadlines` semester path). Given #1's correctness bug, recommend adding a scheduler test (mongodb-memory-server).
- **Rate limit 100 req/15min** is tight for a multi-tab/admin workflow (each dashboard load fires multiple parallel requests); consider 300-500/15min once deployed — noted, not flagged as a defect.
- Whether the controller wants the React Router `future` flags (#19) in this pass or with the future v7 upgrade is a scheduling call — it's a 2-line, cost-free change.
